# RP 自动制卡工作室：初步方案

日期：2026-10-11。当前阶段完成素材检查与方案设计，尚未实现自动生成服务或完成 40 张卡的完整技巧蒸馏。

## 目标和首版边界

用户输入题材、玩法和视觉偏好，系统自动完成需求整理、技能选择、分段生成、组装、检查、局部修复及导出。创作方案与成品提供审核入口。首版支持原创新卡和基于用户卡片的参考创作，不自动投稿，不自动改写原始卡库。

以个人云端工作室为目标：网页界面 + Node 服务与后台任务 + 单用户 SQLite。长任务需保存进度、预算、失败原因和每次产物，支持继续生成及重做单个模块。GitHub 用于源码、技能版本和成品版本管理；生成任务在有后端的运行环境中执行。

## 从卡库蒸馏技巧

先做确定性解析和分类，再用模型提炼设计模式。产物分成三个部分：

1. **技能说明**：适用场景、输入、输出、步骤、失败模式和检查方法。
2. **可组装模块**：玩法循环、状态与事件、人物与关系、世界书骨架、正则/UI 部件及参数。
3. **证据与样例**：源卡 ID、字段位置、版本、正例、反例和演示输入；用户完整卡片保留在私有库。

不能把所有原卡或所有技能包一次塞给模型。需要按新卡需求选择少量相关技能和示例，明确依赖关系、变量名称、输出标签、UI 输入输出协议及冲突关系。优先选恶意代码、山海经、篮球生涯、七日终焉、灰冠学院等不同类型的卡做深度抽样，之后覆盖全部 40 张。

已有卡同时包含小规模机制卡、数百至上万条目的大世界卡和远程内容卡，需分型。远程卡应记录外部依赖与离线完整性，不能只凭 PNG 文件存在就认定素材自包含。

## 生成流水线

需求输入 → 卡型与规模判定 → 游戏循环/人物/主线蓝图 → 技能和例子选择 → 分段生成 → 结构组装 → 触发检查 → UI/正则运行验证 → 局部修复 → 导出与版本存档。

每段必须有结构化输出协议。先确定人物和地点的正式名称、别称、变量与输出标签，再生成世界书和 UI。人物、单场景、多人物、大世界、游戏机制分别使用不同规模预算和模板。主线与阶段机按用户需求启用。

## 过审策略：优先修确定失败

这里的关键词是世界书触发键。首版默认自动修复确定失败，如无触发键、空白键、显式扫描深度为零、正则语法错误和字面 `{{user}}` 等无法工作的触发方式。修复必须保留至少一个可达入口，不能一删了之。

单字或宽泛键结合条目内容与误触发例子判断；必要时替换成具体专名。长名称、三字以上关键词、条目字数、常驻数量等输出提示和证据，不因为长度本身一律删改，也不为满足体量机械灌水。

附件包含有效世界书正文 15000 字符等投稿门槛和人工例外规则。将其作为带来源与版本的投稿配置展示，不能宣称所有短卡、工具卡都绝对不合格；最终过审仍由平台决定。

关键词包存在分歧：旧审核器建议二字兜底，而新 card-flow 要求裸名可达性且不限长度。当前平台源码为大小写不敏感的子串匹配，按最近消息扫描，没有世界书递归扫描。实际触发模拟和反向例句要用于裁决，不能简单用关键词长度决定能否工作。

## 防盗导出

保存三个独立版本：可编辑 JSON、标准 PNG、带作者信息/水印/来源指纹的 RP-Hub 封装 PNG。原始文件不覆盖。

附件的封装去除 `chara/ccv3` 等标准卡块并写入 `RoleplayHubCard` JSON 块，借助平台 JSON 嗅探导入；这是一种兼容封装与防搬运标识，并非密码学加密。每次平台升级都应执行导入与字段一致性检查。

## 平台兼容验证

从当前 `core-utils.js`、`data-services.js`、`runtime-services.js` 固定解析、归一化、关键词触发、正则顺序、HTML 渲染和交互桥接的行为基准。PNG 优先读取 `chara`，随后 `ccv3`，最后 JSON 嗅探；原有素材提取也要审计双块不一致情况。

静态检查与真实渲染检查分开。至少覆盖首次开场、普通回合、状态面板、阶段切换、按钮预填/发送、流式输出完成、JSON/PNG 导入与封装后回读。脚本扫描通过不等于卡片可玩或已经过审。

## 实施顺序和验收

**阶段一：素材与技能库。** 解析全库，生成分类、依赖和来源索引；从代表卡提取并验证第一批可复用技能。验收要求能回答选用了哪些技巧、为何适合、来源在哪里。

**阶段二：最小闭环。** 输入一句需求，生成蓝图、人物、世界书、开场白和基础 UI，导出可导入 JSON/PNG；任务可恢复，超预算停止并保留产物。

**阶段三：检查与自动修复。** 接入确定失败的关键词检查、触发模拟、UI/正则检查以及独立防盗导出；修改展示前后差异，修复后重跑对应验证。

**阶段四：复杂卡与云端体验。** 扩充大世界、复杂机制、阶段剧情和高级 UI；完善项目管理、模型配置、版本回滚及 GitHub 同步。

首版用三种代表类型做验收：人物/场景卡、状态面板机制卡、有阶段推进的大世界卡。检查可导入、可触发、可交互、可续作；AI 品质用实际试玩结果评估，不以“检查全绿”代替。
